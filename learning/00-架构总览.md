# 00 - MewCode 架构总览

## 一、项目定位

MewCode 是一个 **LLM 编程助手 CLI 工具**，对标 Claude Code。用 Java 21 编写，支持三大 LLM 协议（Anthropic / OpenAI / OpenAI Compat），约 134 个源文件、23,000 行代码。

```
MewCode = 终端交互层 (TUI/Remote) + LLM 对话引擎 (Agent) + 工具系统 (Tools) + 基础设施
```

## 二、三种运行模式

```
MewCode.main()
    │
    ├── 默认 → TUI 模式（终端交互式聊天）
    │         MewCodeModel + Program (自研 Elm Architecture)
    │
    ├── -p "prompt" → 非交互模式
    │         PrintMode.run() → 输出到 stdout
    │         支持 --output-format stream-json
    │
    └── --remote → Remote 模式
              RemoteServer (Javalin HTTP + WebSocket)
              浏览器 Web UI
```

三种模式共享完全相同的 Agent 核心——上层只是展示层不同。

## 三、核心数据流

```
用户输入
  → Hook 检查 (pre_tool_use)
  → Permission 检查 (6 层决策链)
  → 注入 Memory + Instructions + Skill context
  → Agent.agentLoop()
      │
      ├─ ① 注入 System Reminders (通知、deferred tools、plan mode)
      ├─ ② Layer 1: ToolResultBudget (超大输出 → 溢写磁盘 → 摘要占位)
      ├─ ③ Layer 2: ContextCompactor (Token 超限 → LLM 摘要 → 压缩)
      ├─ ④ LLM Stream (SSE 流式响应)
      ├─ ⑤ 消费流事件 (text / thinking / tool_call / error)
      ├─ ⑥ 错误恢复 (context too long → compact 重试 / rate limit → sleep)
      ├─ ⑦ 保存 assistant 消息 + 更新 UsageAnchor
      ├─ ⑧ 无工具调用 → break (结束)
      └─ ⑨ 有工具调用 → 执行 → 结果写入对话 → continue (下一轮)
  → 输出到 TUI / WebSocket
```

## 五、设计理念 & 关键决策

### 5.1 自研 TUI 框架
没有使用 Lanterna 等现成框架，而是参照 Go 的 Bubble Tea 自行实现了 Elm Architecture（Model/Update/View）。每一个按键的 escape 序列、CJK 字符宽度、ANSI 渲染都是手写的。

### 5.2 Prompt Cache 优先
整个 `ToolResultBudget` + `ContentReplacementState` 的设计动机是**保证 Anthropic Prompt Cache 命中**。一旦某个 tool_result 被替换为摘要，后续轮次必须使用完全相同的字符串（byte-identical），否则缓存失效。

### 5.3 双层压缩
- Layer 1 (ToolResultBudget) 是**本地操作**，只做文件 I/O，不消耗 LLM Token
- Layer 2 (ContextCompactor) 是**LLM 操作**，消耗 Token 但产出高质量摘要
- 两层各司其职，Layer 1 先执行减少 Layer 2 的输入量

### 5.4 Deferred Tools
MCP 工具默认不发送 schema（`shouldDefer() = true`），只有通过 `ToolSearch` 显式发现后才加载。这防止了数百个 MCP 工具定义撑爆上下文窗口。

### 5.5 UsageAnchor
不用字符数估算 token，而是用 API 返回的真实 usage 数据作为锚点。新增消息在锚点之上做增量估算。这样即使有 Cache Hit（真实 input 远小于字符估算），也不会误判压缩时机。
